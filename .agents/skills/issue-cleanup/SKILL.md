# Issue Cleanup

Grooms the whole open-issue backlog in five phases: **scan → multi-agent verdicts → approval gate → execute → grill**. Everything is verified against the *current code*, never against what issue bodies claim. No GitHub write happens before the maintainer approves the batch (Phase 2).

Paths are relative to the repo root. Prerequisites: `gh` authenticated, `node` on PATH.

**Compliance guardrail (applies to every phase):** issues labeled `compliance`/`question`, or touching `src/lib/isometric/`, GHG math, or protocol requirements are *compliance-sensitive*. They are never closed on code evidence alone — they need protocol/ADR evidence (`docs/isometric/`, `docs/adr/`; the `isometric` MCP server is the authority — call `how_to` first). Issues awaiting Isometric sign-off always stay open. Merges/splits preserve protocol-referencing acceptance criteria verbatim.

## Phase 0 — Scan (read-only driver)

```bash
node .claude/skills/issue-cleanup/scan-issues.mjs <scratchpad-dir>/issue-cleanup
```

Writes `issues-snapshot.json` (all open issues with bodies, comments, closing-PR refs, sub-issue relations; recently-closed issues for dedup; last 100 merged PRs) and `issues-index.md` (one line per issue). Takes ~30s for ~80 issues; paginated GraphQL, well inside rate limits.

**Never `Read` the whole snapshot** (it's hundreds of KB). Extract per-issue slices instead:

```bash
node -e 'const s=require("<abs-path>/issues-snapshot.json");const want=new Set([25,33]);console.log(JSON.stringify(s.openIssues.filter(i=>want.has(i.number)),null,1))'
```

Also load: `CONTEXT.md` (glossary), `docs/adr/` index, `docs/open-questions.md`, `docs/isometric/versions.json`.

## Phase 1 — Verdicts (Claude Workflow, multi-agent)

Run `.claude/workflows/issue-cleanup-verdicts.js` via the Workflow tool (this skill's invocation is the user's opt-in to orchestration):

```
Workflow({
  scriptPath: ".claude/workflows/issue-cleanup-verdicts.js",
  args: { snapshotPath: "<abs>/issues-snapshot.json", indexPath: "<abs>/issues-index.md" }
})
```

Pass `args.clusters: [{ key, issues: [numbers] }]` to scope a run to a subset (also how you re-run `failedClusters` from a previous result). Absolute paths only — subagents don't share your cwd assumptions.

The script: clusters the backlog (sonnet, cheap) → one strong-model agent per cluster verifies every issue against the code and returns schema-validated verdicts → every destructive verdict (`close-*`/`merge`) gets an independent skeptic agent that tries to refute it (refuted or unvetted → fail-safe downgrade to `keep`). Compliance-sensitive issues get the guardrail inside both stages.

Verdict vocabulary:

| Verdict | Meaning | Carries |
|---|---|---|
| `close-implemented` | behavior already exists | file:line + PR/commit evidence |
| `close-obsolete` | superseded by ADR/redesign/newer issue | superseding ref |
| `merge` | duplicate of an older open issue | `mergeInto` (canonical = oldest) |
| `split` | too big for one PR | `proposedSlices` (vertical slices) |
| `enhance` | keep, body stale vs. code | `staleNotes` |
| `grill` | keep, under-specified | `openQuestions` |
| `stakeholder-question` | needs an external answer before work | `stakeholderQuestion` {question, audience, blocks, options} |
| `keep` | already clear | — |

The result also aggregates `stakeholderQuestions` (from any verdict, not just `stakeholder-question`), `downgradedBySkeptic`, and `failedClusters` (re-run these — they are NOT covered).

## Phase 2 — Approval gate (nothing executes before this)

Present ONE verdict table to the maintainer: `# · age · labels · verdict · one-line evidence · proposed action`, grouped by verdict. Use AskUserQuestion for genuinely contested rows; plain review for the rest. The maintainer approves/amends per row. Separately present the **stakeholder question pack** — write it to `<scratchpad>/issue-cleanup/stakeholder-questions.md` (per issue: decision-ready question, audience, what it blocks, options) so it can be shared with DEC/Isometric as-is.

## Phase 3 — Execute (approved rows only; discrete `gh` steps, never chained)

Every posted comment starts with the triage disclaimer line:

```
> *This was generated by AI during triage.*
```

- **Close (implemented / obsolete)** — evidence comment, then close:
  ```bash
  gh issue comment <n> --body-file <comment.md>
  gh issue close <n> --reason completed        # implemented
  gh issue close <n> --reason "not planned"    # obsolete
  ```
- **Merge** — rewrite the canonical (oldest) issue's body to absorb the dupes' substance (`gh issue edit <canonical> --body-file <new-body.md>`), then close each dupe as a duplicate:
  ```bash
  gh issue close <dupe> --duplicate-of <canonical> --comment "<disclaimer> Consolidated into #<canonical>."
  ```
- **Split** — create sub-issues with the `to-tickets` vertical-slice template (What to build / Acceptance criteria / Blocked by, glossary vocabulary), then attach natively and rewrite the parent as an epic overview (like #363's A1–B4):
  ```bash
  gh issue create --title "<type>: <slice>" --body-file <slice.md> --label <labels>
  gh issue view <n> --json id --jq .id     # node IDs for parent + child
  gh api graphql -f query='mutation($p:ID!,$c:ID!){ addSubIssue(input:{issueId:$p, subIssueId:$c}){ subIssue { number } } }' -f p=<parentId> -f c=<childId>
  gh issue edit <parent> --body-file <epic-overview.md>
  ```
- **Enhance** — `gh issue edit <n> --body-file <refreshed.md>`; normalize labels with `--add-label`/`--remove-label` to the existing vocabulary (one category label per issue).
- **Board:** untouched — closed issues auto-move to Done via existing ProjectV2 automation. This skill never edits board fields.

## Phase 4 — Grilling round (interactive)

List `grill` survivors ranked by value. For each, run `/grill-with-docs` with the maintainer (updates `CONTEXT.md`/ADRs as decisions land), then refresh the issue body. Resumable: record grill-pending issue numbers in the final report so a later session continues where this one stopped.

## Phase 5 — Report

Summary with issue links: closed / merged / split / enhanced / pending-grill / stakeholder questions, plus `failedClusters` still uncovered. Stakeholder pack path included.

## Gotchas

- **Workflow args may arrive as a JSON string** depending on the caller — the script tolerates both (`typeof args === 'string' → JSON.parse`). Symptom of passing stringified args elsewhere: `args.snapshotPath` undefined at line 1.
- **Skeptic fail-safe:** a destructive verdict whose skeptic agent dies is downgraded to `keep`, not trusted. Same for `failedClusters` — absent ≠ clean.
- **`--reason` takes `"not planned"` with a space** (quote it); `completed`, `not planned`, `duplicate` are the only values. `--duplicate-of` implies the duplicate reason.
- **Never mutate `agent()`/`parallel()` results in place** inside the workflow script — values crossing the runner's sandbox boundary are cloned (and may be frozen), so in-place edits vanish silently. Rebuild objects functionally (`{ ...v, verdict: … }`). This bit twice during development: skeptic downgrades silently no-oped until the stage was rewritten.
- **Linters flag top-level `return`/`await` in `.claude/workflows/*.js`** as parse errors — false positive; that's the Workflow-runner contract. Reject such review findings with a one-liner.
- **Don't dump the snapshot into context** — always use the `node -e` extraction above; agents in the workflow are prompted with the exact command.
- The snapshot is a point-in-time copy — re-run Phase 0 if issues changed since (e.g. a grilling session on a previous day).
