## Selection rules

The control manages presentation, not completeness, permissions, calculation inputs, or workflow. Initially keep **all editable fields** in Simple, including optional measurements and evidence actions. Detailed reveals existing supplementary readouts, longer explanations and provenance. Any later proposal to hide editable fields is a separate scope decision with validation and discovery requirements.

Keep required inputs, critical derived totals, unresolved/missing-value states, errors, blockers, warnings, locks and corrective actions in Simple. Do not confuse a nullable schema field with an operationally optional field. Saved CERT indicators remain based on saved facts.

Use one control beside the owning sheet title, within the existing header row, without adding vertical space above the form. Do not add controls to every child panel, list toolbar, or page merely for consistency. Retain FormSpine/DetailSpine order and existing sheet behavior. Use Additional Details disclosure inside a Detailed block only when there is a meaningful second layer.

Effort: **S** = about 0.5–1 engineering day; **M** = 1–3 days; **L** = 3–5 days, including focused tests and visual verification. These are planning estimates, not commitments; they assume the approved baseline is available and exclude new data contracts.

## First rollout and later batches

1. **Baseline dependency:** adopt the approved PR #821 implementation through the normal authorized integration process first. Verify the toggle export/import, sheet dirty-event exclusion and record keys in the actual target branch. Do not copy a second competing toggle or silently merge the draft PR.
2. **Batch 1: Deliveries and Applications, create/read/edit together.** Both extend the same physical distribution chain as Product/Order. Delivery first establishes a safe split between mandatory stock feedback and optional provenance. Application then uses saved truck composition. Keep evidence editing and all inputs visible. Estimated 3–6 engineering days total, including shared extraction and verification.
3. **Batch 2: Production Runs.** Reuse the proven pattern with optional Process Flow and compact mass readouts. Consider Feedstocks in the same batch only after comparing the benefit at narrow width; do not hide its allocation warning or justification. Estimated 2–4 days for the pair if Feedstocks is adopted.
4. **Batch 3: Credit Batch read mode only**, after reviewing a concrete content map of lifecycle, readiness, membership, chemistry and technical context. Do not extend its create/edit by symmetry. Estimated 3–5 days.
5. **Later opt-ins:** stock reconciliation after the Delivery preview extraction; Lab Sample read only if a mockup demonstrates a useful reduction while retaining results and eligibility. No default commitment to either.

At the time of the inventory, the next decision was whether to authorize Batch 1 (subsequently authorized; see implementation outcome). No decision blocks this inventory. Separate future decisions are whether specialist read surfaces merit the control and whether any optional editable fields should ever be hidden; the current recommendation is to keep all such fields visible. If those questions become deferred product work, record them in [open questions](../../open-questions.md), rather than treating this proposal as authorization.

## Implementation seams and constraints

- Keep detail state in the feature body, separate from RHF values and persisted domain objects. Prefer keyed read children through `viewModeChildren`; do not put React state inside a plain sections builder. Keep the outer EntitySideSheet mounted as prescribed by the design system.
- The Delivery preview extraction must expose a mandatory summary/status area independently of optional graphics. Existing callers retain current behavior by default. Do not change Product/Order or reconciliation globally as an accidental consequence of editing `OutputStockPreview`.
- Reuse existing formatters, mass precision, Missing Value tokens, and canonical calculation functions. For unmixed mass use compact/inline `MoistureSplit`; for blends use conserved dry biochar and its existing composition model. Do not copy Product composition math into unrelated entities.
- Detailed data may load lazily only when genuinely optional. Hiding graphics cannot disable a preview query that validates availability or provides submission blockers. All fetches retain organization/facility query scope and server authorization.
- Preserve immutable product, delivery and application allocations. A read view renders saved facts; history/current availability is separately labelled. Editing a date or moisture never gains permission to rewrite a frozen allocation from this UI work.
- Keep existing upload queues, live evidence actions, nested dialogs, form footer and unsaved-change guards intact. Do not unmount a stateful upload/editor subtree merely to hide explanation.
- Tinted blocks use the approved light surface token, measured spacing and explicit body typography; avoid new cards around each field. The radio control and disclosure labels remain consistent with the approved baseline.

## Acceptance criteria for each adopted surface

1. **Three modes:** create, saved read, and permitted edit start in Simple. Switching records, reopening a sheet and moving read → edit → read reset as designed; returning to the same open body does not unexpectedly erase form values. No localStorage/global preference is introduced.
2. **Presentation-only change:** toggling Simple/Detailed repeatedly leaves input values, RHF dirty/touched state, validation results, document queues and submitted payload unchanged. Toggling alone followed by Close/Cancel/Escape shows no discard prompt. A real edit still triggers the existing guard.
3. **Safety visibility:** test missing inputs, server error, stale/failed preview, insufficient stock, locked record and any warning with Simple selected. Every required action and disabled-submit explanation remains visible. Do not rely on a hidden child mounting to discover a blocker.
4. **Saved versus current:** save a Delivery/Application, change upstream stock, then read it in both modes. Saved wet/dry values and source allocations remain identical; explicitly labelled current availability may differ. Late intake does not rewrite saved attribution. Toggle changes must not cause a mutation.
5. **Specific business cases:** Delivery with multiple FIFO layers and a blocked correction; Application with partial truck usage, multiple source shares and a certification lock; Production Run with missing moisture, failed/cancelled status, multi-bin input and a readings-file queue. Credit Batch later adds missing run data, claimed inputs, outlier chemistry and capped estimate. Preserve existing authorization denial tests.
6. **Keyboard and focus:** native radio semantics, visible focus, arrow-key selection, keyboard disclosure activation, no focus loss when context collapses. If a future implementation can hide focused content, explicitly restore focus to its controlling element. Error focus must never target hidden/unmounted inputs.
7. **Accessible meaning:** values and units available as text, not solely bars/color. Missing data is not zero; loading and error states are announced appropriately. Disclosure exposes expanded state. The compact control remains usable at narrow width and zoom.
8. **Visual evidence:** compare against approved Product/Order at 1440px and 390px, plus keyboard/zoom checks. No horizontal overflow, clipped amounts, oversized default heading typography, nested card clutter or footer collisions. Verify long names and multi-layer data, not just a one-row happy path.
9. **Verification scope:** add focused component tests for mandatory/optional boundaries and dirty-state behavior, then browser flows covering actual create/save/read/edit plus no-change close. Run `pnpm lint`, `pnpm typecheck`, targeted component tests and relevant existing distribution/FIFO specs. Broaden only for shared-component changes or uncovered risks. Follow [testing](../../testing.md) and the repository UI-verification skill at implementation time.

## Implementation outcome

The user authorized the rollout after the inventory. A reusable native-radio `FormDetailToggle` and scoped presentation provider now put Simple | Detailed beside the existing sheet title. Detail state resets on record, mode, and open changes without remounting form inputs or creating dirty changes.

- Delivery, Application, Production Run and Feedstock sheets adopt the control across create/read/edit.
- Credit Batch read mode hides optional formula/component metadata; Sample read mode shows the control only when transport provenance exists.
- Output-bin reconciliation and stock correction reuse compact stock consequences in Simple, with graphics and allocation breakdowns in Detailed.
- All editable inputs, missing states, warnings, blockers, evidence actions and critical totals remain visible in Simple. Short forms and existing certification disclosures remain unchanged.
- Product/Order PR #821 was used as a reference and was not merged or rewritten by this rollout. Its toggle API remains compatible; final integration should resolve the shared files against the header placement implemented here.

Browser verification passed nine tests covering 1440px and 390px layout, keyboard selection, clean close, read/edit resets, preservation of edits, real saves, FIFO shortages, saved allocation shares and stock corrections. Focused component tests and TypeScript checking passed. An independent code review found no actionable regressions. No production data, schemas or authorization behavior changed.

The original ranking is a source-based design recommendation, not observed user-frequency data or a runtime accessibility certification. Evergreen usage guidance is in [Forms](../../forms.md).
