## Summary

The four asks were: more simplification, a clean and future-ready way of talking to the Certify registry, less test redundancy, and faster build and test. The scan produced 125 candidate findings from two models across ten lenses; a three-stage adversarial pass kept 94 of them, with corrections. The headline is not the line count. It is that the registry integration has one good seam (`performRegistryCreate`, the create-or-reconcile choreography) and five things around it that every lifecycle re-implements differently: how the client is obtained, how a record is looked up by reference, how the mirror row is persisted under a race, how drift and audit identity are recorded, and how the outcome is handed back. Fixing those five, in that order, removes most of what makes the integration feel like a mess without a rewrite.

Three facts found along the way change priorities more than any refactor:

- The daily Isometric health workflow has failed on every one of its last 109 runs since 2026-05-26. The step that would detect registry schema drift sits behind the failing step and has never executed. The generated Certify types have been stale since 2026-06-10.
- An incomplete registry page scan currently reads as "record absent", and the next step is a non-idempotent POST. That is a duplicate-record hole in the idempotency story, and it is a ten-line fix.
- The vitest suite runs in 37 seconds on the owner's machine and 303 seconds on CI. Test execution is 45 seconds of that. The rest is import graphs: 117 test files load the database module transitively while asserting for 1.9 seconds in total.

What to do first, in order: Part 1 (eight small defect fixes, one PR each), then the first three slices of Part 2 (credentials out of the lib, one lookup primitive, typed create result), then Part 5 (the three measured CI caches), then the rest as capacity allows.

## Verified facts that change priorities

### The health workflow has been dark since May

`.github/workflows/isometric-health.yml` runs daily. Its coverage-check step imports the Isometric barrel; `src/lib/isometric/client.ts` imports `@/config/env` at module scope, and that file validates the whole application environment, so the job dies on missing `DATABASE_URL`, `NEXT_PUBLIC_APP_URL` and `BETTER_AUTH_SECRET` before it reaches the "Detect Certify OpenAPI drift" step. 109 of 109 runs since 2026-05-26 failed this way. Consequences:

- `src/lib/isometric/generated/certify.d.ts` was last regenerated on 2026-06-10. Against types generated from the live spec on 2026-09-08 it differs by 315 lines: two new paths (`/monitoring_submissions` and its requirements sub-path) and one new schema. Nothing the app calls has changed shape.
- `src/lib/isometric/generated/mrv.openapi.json` (12,779 lines) is read by no code, is not the input of the regenerate script (which fetches the URL directly), was committed once on 2026-05-05, and lacks the entire `/ghg_entries` family the code already uses. Yesterday's analysis kept it under "not worth touching" on the premise that it is regenerated; it is not.
- The coupling is at the logger, not only the client: `src/lib/log/index.ts` reads `env` for the log level, and three lib modules import the logger. Cutting the env read there fixes every importer at once.

### What the registry actually allows

From the live spec and the Isometric documentation (authoritative: https://docs.isometric.com/api-reference/standards, https://docs.isometric.com/user-guides/certify/supplier-reference-id, https://docs.isometric.com/user-guides/certify/modifying-resources, https://docs.isometric.com/user-guides/certify/storage-sites, https://docs.isometric.com/user-guides/certify/project-assets/introduction):

- A `supplier_reference_id` list filter exists for components, datapoints, feedstock types, GHG entries, measurement locations, removals, sources and storage units. It does not exist for storage locations, biochar applications, production batches, measurement samples, sensors or GHG statements. Reconciliation for those six is a client-side scan over Relay pages of at most 50. There is no single-object GET by reference. So the code has exactly two lookup strategies, forced by the registry, and today it has seven implementations of them.
- No outbound webhooks. No idempotency keys on POST. Isometric's own guidance is a local mapping table plus lookup before retry, which is what the mirror tables and the submission ledger already are. GraphQL (`projectEvents`, `asyncProcesses`) is the recommended read path for nested readback and for tracking asynchronous state.
- The MRV API is `/mrv/v0`; Isometric promises no breaking changes only for versions above v0. Clients must tolerate new endpoints, new optional query parameters and new response properties.
- PATCH exists for datapoints, components, removals, GHG entries, storage locations and sources; not for GHG statements, biochar applications, production batches, measurement samples or sensors. Changes that affect calculations become visible to the verifier only after `POST /ghg_statements/{id}/submit`; `pending_total_co2e_removed_kg` on the statement is non-null exactly when resubmission is needed. Previous versions cannot be queried and never will be.
- The project-assets model (sites, activities, materials, each with a type, a supplier reference and links) is live for two other protocols and "other protocols will be migrated to the same model in the near future". For biochar, storage locations are sites, biochar applications are activities, and feedstock or production batches are materials. This should shape names now and code later.

## Part 2: The Certify interaction

### Diagnosis

Using the design vocabulary (module, interface, depth, seam, adapter, leverage, locality):

1. **The deep module exists and is good.** `src/fn/certification/registry-create.ts` owns POST-or-reconcile, reconcile-before-POST on resume, the mutation-possible classification, ledger rejection and both audit events. It has seven callers in six files and two real adapters in tests. It is the seam to build on, not around.
2. **Its interface returns too little.** It returns `{ externalId, source }`, so every caller keeps a mutable closure to capture the resource it already received, and then checks an impossible state after the await. Storage locations even carry a type assertion with an apology in a comment. A generic result (`performRegistryCreate<T>` returning the typed resource) removes that pattern at four call sites and is the cheapest deepening in the whole report.
3. **Client acquisition is a leaky seam in three ways.** The lib reads app configuration at import; `getIsometricClientForOrg` dynamically imports data-access from inside the "pure" lib and takes a bare organisation id with no scope guard; and credentials are decrypted on every resolution. There are 29 production resolutions in 21 files, once per action plus once per nested lifecycle, so one Removal submit resolves them again per application and per intent. The fix is placement, not a new abstraction: resolution belongs in data-access with an `OrgContext`, the lib exports `createIsometricClient(credentials)`, and fn resolves once per action and threads the client, which 62 sites already do.
4. **Lookup by reference is one concept with seven implementations in four shapes.** Two 51 and 57-line bounded loops that differ by a guard and their copy; two unbounded first-match scans over the generic paginator; a server-filter helper copied verbatim between two files; a sensor lookup on a different field. One primitive (`findByReference` with a server-filter or scan strategy, a bound, an opt-in uniqueness check and one incomplete-scan failure) makes the eight named wrappers one-liners, and closes #628 and #281 as a side effect. Uniqueness must be opt-in: production batches and measurement samples rely on first-match today.
5. **The outer choreography is where the duplication lives.** Around the create seam, storage locations, biochar applications, production batches, measurement samples, sources and sensors each answer the same questions with their own names and policies: which lookup, how to persist the mirror row under a race (five conflict policies with three outcomes, one documented backwards), what to do on a journal hit, how to record drift (three models, three vocabularies, comparators in two tiers), which identity the sync event carries (production-batch events land under the Removal id; operation prefixes are spelled `ghg_statement:` in one place and `x-y:` everywhere else), and how to tolerate a 404. The measured envelope is 1,199 lines of caller code around the 347-line seam. The right move is a spec-driven lifecycle module (ensure, refresh, release) that the entity modules configure, but the line estimate should be withdrawn until a spike on storage locations plus biochar applications proves it; and sources must be last, because their persist runs inside an open transaction and their reconcile can upload.
6. **The two submission paths share the claim and re-implement what follows it.** Removal and GHG Statement both use `claimSubmissionDraft`, then each thread lock identity, track possible-or-confirmed mutation, write identity, finalize and preserve an interrupted draft in their own words across four files per path. Two helpers (record claimed identity; persist claimed-attempt interruption best-effort) parameterised by entity copy remove the copies without a new "attempt" abstraction. The GHG verifier submit does not use the claim at all, updates an existing external statement under a session lock, and classifies HTTP 409 as ambiguous where the create seam classifies it as definitive; `docs/architecture.md:234-238` says the two paths are identical, which is false and should be corrected first.
7. **The ledger's state machine is spread over six files** and three CAS predicates. Moving the ledger half of `certification.ts` (about 485 lines) into a `submission-ledger.ts` data-access module with one private `draftLockPredicate(ctx, id, expectedLockedAt?)` brings that file well under the cap and gives the verbs one home. ADR 0008 allows internal reorganisation and requires real-database contention tests for it.
8. **The barrel is a namespace, not a seam.** `src/lib/isometric/index.ts` re-exports 139 lines mixing the client, seven of ten endpoint modules and seven of seventeen utilities; 116 deep imports versus 40 barrel imports in the app tiers, and 44 of the deep ones target modules the barrel already exports. Enforcing it (#366) would rewrite about 137 import lines for zero depth. The better move is to shrink it to the registry-facing surface (client factory, error type and helpers, links, endpoint modules), keep a separate browser-safe links entry, and move the two utilities that import `@/lib/certification` at runtime (`submission-claim.ts`, `ghg-statement-state.ts`) out of the lib. That gives #366 and #368 a small surface to put an interface on if a second certifier ever exists.
9. **Vocabulary.** "Reconcile" names three unrelated behaviours (a supplier-reference lookup, a create-or-adopt of a dependent artefact, and a registry-to-local mirror sync), and the audit trail uses the same word for two of them. Fix the glossary in `CONTEXT.md` first (Reconcile = bring local mirror rows into line with observed registry state; Look up by reference; Ensure = create-or-adopt and verify), then rename only the four colliding functions.

### How the shape was chosen

Three designers worked independently from the verified findings, the registry facts and the code: one told to deepen in place with the smallest interface changes, one told to design one deep registry module, one told to design for where the registry is going but build only what pays now. All three converged on the same first six moves, with near-identical interface sketches: credentials become an input of the HTTP client and the lib stops reading application configuration; credential resolution moves to data-access behind an `OrgContext`; one lookup primitive carries the two registry-forced strategies and a completion contract; the create-or-reconcile seam returns the typed confirmed resource and takes its audit identity as one value; deletion outcomes become a list of typed records; the fake registry becomes the single double at the HTTP seam. They split on one thing: whether to build a spec-driven ensure/refresh/release engine over the six mirror lifecycles now. The "one deep module" design builds it, but sets its own stop rule: if a spike on production batches plus storage locations does not remove at least 150 lines across those two files, stop after the shared slices. The other two defer it with a trigger: the engine gets a second policy-identical adapter only when the registry's project-assets model reaches biochar and storage locations, biochar applications and production batches become sites, activities and materials. The recommendation below takes the six shared moves as the plan, adopts the engine as a gated spike, and takes the "one module" design's audit staging and its per-handle call budget as grafts.

**Panel verdict.** Three judges (depth and locality; migration safety; future fit without speculation) scored the designs independently and all three ranked them the same way: deepen in place first, credentials-in-resources-out second, the single deep module last. Scores out of 10, in that order: depth 8/7/5, locality 7/6/5, preservation 7/6/5, reviewability 7/6/4, YAGNI discipline 9/7/4, alignment with the registry facts 9/6/7, future fit 6/6/7. The judges' corrections are folded into the slices below and are worth stating on their own:

- The Source lifecycle writes its secondary audit grain (the document event also filed under the Removal) only on failure. Any shared identity helper must keep that failure-only rule; a design that filed success and unlink events under both grains would change the audit trail.
- Deleting released Source mirrors in the registry after the finalising transaction commits is not safe as sketched: the document-upload data-access explicitly lets a later mirror reconcile onto the same remote Source, under its own transaction lock, so a concurrent mirror can adopt the Source before the post-commit DELETE and a successful DELETE would then invalidate that new mapping. Remote Source deletion needs coordinated retirement and an eligibility recheck under the mirror lock. The records list (M12) is still right; the Source kind waits for that design.
- "Fail loud" is not guaranteed for deletion tests against the fake registry: an unmodelled route throws an error the deletion path reads as "absent". The fake must distinguish unsupported routes from modelled absence before deletion tests move onto it.
- A callback-based insert-or-get helper adds little depth; two judges would defer it. M9 is therefore optional.
- Four files sit at or one line under the 1000-line cap (`submit-removal.ts`, `certify-context-core.ts`, `certification.ts`, and the fake registry at 740 and growing); any slice that adds lines to them must extract in the same PR.
- None of the three designs completes #632 or #641. The typed result and the audit identity make them cheaper; the replacement identity, dependency rebinding and retirement that #632 needs, and the compiled plan frozen in the authoritative snapshot that #641 needs, are their own work.

### Recommended shape

Seven modules, in the design vocabulary. Interfaces are sketches; every invariant named is one the code already has and must keep.

**1. The pure client.** `src/lib/isometric/client.ts` exports `createIsometricClient(credentials: IsometricCredentials | null): IsometricClient` and `IsometricCredentials { clientSecret; accessToken; baseUrl }`, and imports neither `@/config/env` nor data-access. The interface shrinks to six members (`get`, `post`, `patch`, `delete`, `paginate`, `paginateAll`); `request`, `headers` and `allowUnsafeRetries` go (no caller), `signal` stays for #649, the environment type becomes `keyof typeof BASE_URLS`. Invariants kept: a null credential set throws `not_configured` at request time with today's message, never at construction, because five branches and one piece of copy depend on that timing; idempotent methods retry three times with Retry-After capped at 30 seconds; POST and PATCH never retry; the per-attempt timeout is 30 seconds and now covers body consumption (D6). `paginate` throws on a missing or repeated cursor instead of returning early. A 15-line `client-env.ts` with its own three-field zod schema is the only lib file that reads `process.env`, for the two scripts, the sandbox integration test and the health job; the barrel keeps re-exporting it so no script retargets. The logger stops importing `env` (it parses `LOG_LEVEL` locally), which is what makes the whole lib importable without a database.

**2. The credentials resolver.** `src/data-access/certifier-credentials.ts` gains `resolveIsometricClient(ctx: OrgContext, target?: { organizationId })`: `requireOrgScope`, the `organizationId` predicate, the existing platform-admin guard for the one cross-organisation caller (credential verification after save), decrypt, pair with `env.ISOMETRIC_ENVIRONMENT`, construct. No caching: rotation is observed on the next resolution exactly as today. The 29 production call sites in 21 files retarget the import and pass `ctx` instead of a bare id; the sensor data-access file imports it from data-access, which is why the resolver cannot live in fn. About 24 test files retarget one mock from the lib to this function; a missed retarget hits the real resolver and fails loudly on the database read, not silently.

**3. The lookup primitive.** A new file under the lib's utils folder, find-by-reference (about 95 lines), exports `findByReference<T>(client, spec)` with `spec.strategy` either `{ kind: "server-filter", field, pageSize }` or `{ kind: "scan", unique, pageSize, maxPages }`, plus wrapper-supplied verbatim copy for the duplicate and exhausted cases. Invariants: `unique: false` returns the first match (production batches, measurement samples, sensors, datapoints, GHG entries, sources); `unique: true` completes the bounded traversal and throws on a second match (storage locations, biochar applications); a missing or repeated cursor throws "incomplete scan" and a truncated traversal never returns null; an exhausted bound throws the entity's exhausted copy; `maxPages` undefined means unbounded, which keeps the two currently unbounded scans behaviour-identical until the owner sets a bound (Q1). The eight wrappers keep their names and `(client, ref)` signatures and become one-liners, because six callers pass only those two arguments. Scan mechanics tests move to one file; each entity test keeps one wiring case.

**4. The typed create-or-reconcile seam.** `performRegistryCreate<T = string, P = void>` in `src/fn/certification/registry-create.ts` returns `{ value: T; externalId; source; persisted: P }`; `reconcile` returns `ReconcileLookup<T>` with `{ found: "single", value }`; `onConfirmed(value, externalId)` runs before the success event and its return is carried; `externalIdOf` is required only when `T` is not a string, so the three identity-only callers (datapoint, removal, GHG statement create) change nothing but types. The audit triple becomes one `audit: RegistryAuditIdentity` value built by per-kind constructors in a new `registry-audit.ts` (about 75 lines) that also absorbs `appendSyncEventBestEffort`, the two-grain Source failure pattern (`alsoUnder`), the audited-call copy in deletion, and a `stage`/`flush` pair for the one lifecycle that must write inside a transaction. Every existing `(entityType, entityId, operation)` string is reproduced verbatim and pinned by a snapshot test; the grain change for production-batch and measurement-sample events is the owner's (Q2). The four mirror callers lose their mutable closures and impossible-state throws; the five test files that re-implement the algorithm run the real module against the fake registry with ledger effects stubbed at data-access.

**5. Three small helpers.** `describeIsometricFailure(error, fallback)` in `error-utils.ts` returning `{ message, body, registry }` for the five describe and four sanitise sites, with presentation policy left at each caller. `insertOrGetMirrorRow(ctx, executor, insert, reselect, label)` in `data-access/utils.ts` for the three writes that are genuinely insert-or-get; the executor parameter is mandatory because the Sources write runs inside its mirror-lock transaction. The pure comparators (`storageLocationMismatchMessage` with its coordinate tolerance, `productionBatchMismatchMessage` with the legacy window) move beside the request builders they compare against, and drift becomes one value shape `MirrorDrift = { reason; details } | null` fed to the three existing per-table writers.

**6.
