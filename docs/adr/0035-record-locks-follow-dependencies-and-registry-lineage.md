# Record locks follow dependencies and registry lineage

Use one pure predicate per record kind for Open, In use and Sent. Data-access resolves numeric consumers and every certification ledger version, then applies that predicate for server writes, REST, MCP and advisory reads. A failed latest attempt cannot hide an earlier registry submission. Unknown states fail closed.

Sent begins when registry creation starts. Reopening requires a fresh covering statement in FAILED_VERIFICATION, or DRAFT with evidence of earlier verifier submission, no other blocking or unknown statement, and no in-flight work. Certify's `submitted_at` counts regardless of whether noma or the Certify web UI submitted it. Mutations resolve this under the existing artifact locks and refuse newly discovered unlocked artifacts. Each remotely effective Removal attempt must be covered by the fresh statement and predate return evidence. REST has no return timestamp, so its verifier-submission timestamp supplies a conservative lower bound. Missing historical submission evidence keeps Sent. Reopening removes Sent, not existing numeric dependencies.

Output-stock form edits use the same dependency check as correction posting (ADR 0029). Unrelated intake alone does not lock an entry; later dependent draws, counts and applications do. Feedstock keeps its wet-lane integrity rule (ADR 0027): corrections remain possible while later withdrawals still fit. Posting invariants and stock sufficiency remain separate from record locks.

Keep the existing `certification_locked` domain code and HTTP 409 problem mapping for lock refusals, including In use. This preserves existing certification clients and transport adapters instead of introducing a second lock code. Messages name the holder and the action needed to free the record. The predicate declares fields the current write paths accept while In use, subject to their ordinary validation. See [record-lock follow-ups](../open-questions.md#record-lock-follow-ups) for free-field changes, deletion reversals and remaining independent guards.

Verifier submission takes the facility durability lock before the GHG Statement artifact lock, and retains the artifact lock through provider I/O and committed local finalization. Source writers use the same artifact key and re-read after waiting. Advisory history reads batch their targets and share statement evidence within the request.
